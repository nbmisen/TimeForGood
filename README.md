# TimeForGood

TimeForGood is a native iOS scheduling and focus app: finish your day, earn in-app rewards, and later support verified charity donations.

> **当前状态：本仓库目前仅完成项目初始化。** 这里还没有可运行的 iOS 应用，也尚未部署 Supabase、接入真实账号，或配置任何密钥。下面描述的是产品愿景与技术方向，不是已经交付的功能。

## 愿景

TimeForGood 计划做成一款原生 iOS 日程与专注应用，时间线体验接近 Structured 的按日安排：把一天的任务和时间块清晰排开，并围绕“完成计划”形成正向反馈。

完成日程与专注后，用户将获得**应用内游戏资源**，用于解锁装饰、功能或奖励。这是产品核心循环的一部分，也是近期要验证的方向。

更远期的设想是：赞助商可以提供小额赞助，用于用户可核验的活动；款项将捐给用户选择的慈善机构。这一部分仍属于愿景，**当前没有赞助商，也没有支付或捐款能力**，不会把公益资金写成已经上线的功能。

未来若推进公益赞助，公益资金与应用内游戏资源必须分开预算、分开记账，并可独立核验，不能混用。

## 当前 MVP 范围

近期只做 iOS 上的核心调度与同步能力：

- 原生 SwiftUI iOS 应用
- Today 任务的创建、编辑、完成
- 离线持久化，以及联网后的及时同步
- 冲突检测与可处理的冲突界面（第一份 PR 采用拒绝过期版本、由用户选择的最小策略）

本次初始化不包含上述实现，只记录范围，方便后续第一份 PR 开工。

## 架构选择

- **客户端：** SwiftUI。选择原生 iOS，是因为开发者本人是 iOS 开发者，也为了把 MVP 范围收在一个平台上。
- **本地持久化：** Core Data，本地优先。当前不使用 SwiftData，以避免尚不成熟的抽象带来额外复杂度。
- **后端：** Supabase（Auth、Postgres、Row Level Security、数据库 RPC）。
- **同步：** 自建持久化 outbox / 操作队列，而不是依赖 Supabase 对 Core Data 的开箱即用同步（Supabase 并不提供这一层）。
  - 本地变更与对应的待同步操作在同一个 Core Data 事务中写入。
  - 每个操作带有唯一 `operation_id`，服务端按认证用户与操作 ID 做幂等处理，避免重复提交被执行两次。
  - 使用服务端版本检测冲突，不以设备时间戳决定谁赢。
  - PostgreSQL 以原子事务处理同步、去重与冲突结果。
- 不同步连续后台同步的承诺；在应用启动、回到前台、以及运行中恢复网络时同步。

## 第一份 PR 要证明什么

第一份开发切片只证明“离线完成任务，并能安全同步”，而不是做完整产品。预期包括：

1. Today 屏幕：创建带标题和计划时间的任务，可编辑，可标记完成；离线可用，重启后仍在。
2. 每次本地变更与 pending sync operation 写入同一 Core Data 事务。操作需包含唯一 `operation_id`、任务 ID、基准服务端版本，以及明确的变更字段或动作。
3. Supabase 迁移：tasks、操作回执表、需登录才能调用的同步 RPC；启用 RLS，并在 RPC 内强制用户归属。应用中不得放入 service-role key。
4. 每个操作在 PostgreSQL 中原子处理：按认证用户与 `operation_id` 去重，重试返回原结果，并串行化对同一任务的并发更新。不以设备时间戳裁决冲突。
5. 本阶段若基准版本过期，则拒绝自动字段合并：返回当前服务端任务，保留本地待同步编辑，并提供简单冲突界面（“保留服务端版本” / “应用我的修改”）。应用本地修改时，必须基于最新版本提交新操作，并允许再次冲突。
6. 在应用启动、进入前台、以及运行中恢复网络时同步。拉取服务端变更并应用到本地时，不得再生成新的出站操作；仅在服务端确认后再清除 pending operation。若服务端已提交但响应丢失，必须可安全重试。不承诺 iOS 持续后台同步。

需要测试：离线持久化、本地数据与 outbox 的原子写入、重复提交、丢失确认后的重试、并发更新、过期版本冲突，以及跨用户访问拒绝。使用本地 Supabase 或一次性测试环境，不使用生产环境。

## 非目标（现阶段明确不做）

- Android、桌面端、React Native、Electron 或其他跨平台方案
- 完整专注计时器、重复任务、游戏化的完整系统
- 支付、捐款、赞助商后台，或任何资金流转
- 声称已有赞助商，或把公益赞助写成已上线能力
- 自动字段级合并（第一份 PR 先做版本拒绝与用户确认）
- 部署生产 Supabase，或在仓库中存放密钥、service-role key、个人访问令牌
